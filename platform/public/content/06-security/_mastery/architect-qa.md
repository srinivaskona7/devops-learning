# Architect Q&A — Security

60+ Q&A for senior, staff, and architect-level Kubernetes and cloud-native security decisions. Covers multi-tenant boundaries, supply-chain SLSA L3 program, OIDC trust to cloud, secret rotation at scale, runtime detection at scale, zero-trust mesh adoption, compliance program design, and incident response playbooks.

---

## Multi-tenant security boundaries

### Q1. What is the strongest tenant boundary in Kubernetes?
A separate cluster. Namespace isolation is a soft boundary — node, kernel, and control-plane are shared. For hostile multi-tenancy, use cluster-per-tenant or vCluster + node pool isolation + gVisor/Kata.

### Q2. When is namespace-per-tenant acceptable?
Cooperative tenants (same company, internal teams). Enforce: NetworkPolicy default-deny, ResourceQuota, LimitRange, RBAC scoped to namespace, no shared CRDs that leak data, PSA restricted.

### Q3. How do you prevent a tenant from reading another tenant's secrets?
RBAC scoped to namespace, no ClusterRoleBindings granting cross-namespace get on Secrets, encrypt-at-rest in etcd with KMS, audit on Secret access, External Secrets per-namespace SA with IRSA scoped to tenant prefix in the secret store.

### Q4. How do you stop tenants from consuming all node resources?
ResourceQuota for cpu/memory/pods, LimitRange defaults, PriorityClass for system workloads, dedicated node pools per tier with taints + tolerations, scheduler with anti-affinity.

### Q5. What is vCluster and when do you pick it over namespaces?
vCluster runs a virtual control plane inside a host namespace. Picks: tenants need cluster-admin for their own scope, want their own CRDs, version skew. Caveat: still shares host nodes — not a hard isolation boundary unless combined with sandbox runtime.

### Q6. How do you prevent privileged escalation across tenants?
Pod Security Admission `restricted` on tenant namespaces, baseline on system, drop ALL caps, no hostPath, no hostNetwork, no privileged, seccomp `RuntimeDefault`, read-only root FS. Validate via Kyverno or Gatekeeper as belt-and-suspenders.

### Q7. How do you isolate tenant traffic east-west?
Cilium with cluster-mesh and tenant labels; default-deny NetworkPolicy; per-tenant L7 policies for shared services; egress via per-tenant gateways; mTLS via mesh with SPIFFE IDs that encode tenant.

### Q8. How do you handle shared cluster-scoped resources like CRDs and webhooks?
Platform team owns CRDs. Tenants get RBAC only on namespaced custom resources. Validating webhooks must be tenant-aware via namespace selectors. Conversion webhooks run with platform identity, not tenant.

### Q9. How do you prevent noisy neighbor in storage?
Per-tenant StorageClass with IOPS/throughput limits, CSI quota, ceph/EBS namespace-scoped pools, monitor PVC consumption with quotas.

### Q10. What is the audit strategy for multi-tenant?
Audit policy: log Metadata for all, RequestResponse for tenant Secret/ConfigMap writes. Stream to per-tenant index in SIEM. Retain 1 year. Tenants get read on their slice via API.

## Supply-chain SLSA L3 program

### Q11. What is SLSA L3 in one sentence?
Builds run on a hardened, hosted, isolated builder that produces non-forgeable provenance signed by the platform.

### Q12. What are the L3 hard requirements?
Hosted build platform (no self-hosted runners with mutable state), isolated build per invocation, parameterless build entry, hermetic where possible, signed provenance generated by the platform key.

### Q13. How do you reach L3 with GitHub Actions?
Use GitHub-hosted runners (or actions-runner-controller with ephemeral pods), use the SLSA generic generator workflow, sign with sigstore keyless using the GitHub OIDC token, attach in-toto attestation to the OCI registry via cosign.

### Q14. How do you verify SLSA provenance at admission?
Cosign policy controller or Kyverno `verifyImages` rule with the predicate type `slsaprovenance` and an issuer/subject regex matching your build platform's OIDC identity.

### Q15. Where do attestations live?
As OCI artifacts referenced by digest in the same registry. `cosign download attestation registry/app@sha256:...` returns DSSE envelopes containing in-toto statements.

### Q16. How do you handle base image trust?
Pin by digest. Rebuild base images in your own pipeline producing your own provenance. Mirror upstream into a private registry with a verification policy that requires either internal provenance or vendor signature.

### Q17. What is the rollout plan for SLSA L3 across 200 services?
Phase 1: instrument top 10 critical services, pilot signing and verification in staging with `--enforce=warn`. Phase 2: enforce in staging, warn in prod, build dashboards. Phase 3: enforce in prod for tier 1, expand cohort by cohort. Phase 4: deny unsigned by default.

### Q18. What gets signed and what gets attested?
Sign: container images, Helm charts, OCI artifacts. Attest: SBOM (cyclonedx/spdx), SLSA provenance, vulnerability scan results, test results, custom predicate types (e.g. internal review approval).

### Q19. How do you prevent dependency confusion?
Private registry first in resolver config, scope locks, pin transitive deps, mirror approved deps only, block public installs in CI behind explicit allowlist.

### Q20. How do you handle SBOM at scale?
Generate at build with syft, attach as attestation, push to a central SBOM store (DependencyTrack or Snyk), continuously scan against fresh CVE feeds, alert on new CVEs against deployed digests.

## OIDC trust to cloud

### Q21. Why use OIDC federation over static cloud keys for K8s workloads?
No long-lived secrets in cluster, automatic rotation by IdP, fine-grained policies bound to the workload identity, audit on the cloud side.

### Q22. How does IRSA work in EKS?
EKS issues OIDC tokens to ServiceAccounts. AWS IAM trusts the cluster's OIDC issuer URL. The pod's projected SA token is exchanged via STS AssumeRoleWithWebIdentity. The workload assumes a role scoped via condition keys on `sub` matching `system:serviceaccount:ns:sa`.

### Q23. How do you trust GitHub Actions to deploy to AWS without a static key?
Configure AWS IAM OIDC provider for `token.actions.githubusercontent.com`. Create a role with trust policy conditioning on `sub` like `repo:org/repo:ref:refs/heads/main` and `aud=sts.amazonaws.com`. Use `aws-actions/configure-aws-credentials@v4`.

### Q24. What is the equivalent for GCP?
Workload Identity Federation. Create a workload identity pool, add provider with the OIDC issuer, bind a service account with `principalSet://...` condition.

### Q25. What is the equivalent for Azure?
Azure Workload Identity for AKS, federated identity credentials on a managed identity referencing the OIDC issuer URL.

### Q26. How do you scope tokens minimally?
Use audience claim restriction, short TTL (1h max), conditions on `sub` for exact SA, branch-or-tag restriction in CI, never wildcard `repo:org/*`.

### Q27. How do you rotate the cluster OIDC signing key?
Managed services rotate automatically on EKS/AKS/GKE. For self-hosted, rotate kube-apiserver `--service-account-signing-key-file` with overlap window, publish JWKS, update IAM provider thumbprint if needed.

### Q28. What is the failure mode if OIDC issuer URL is wrong?
Workloads cannot assume cloud roles, deployments stall on cloud calls. Mitigation: monitor STS errors, alert on AccessDenied spikes, runbook to verify OIDC provider thumbprint and issuer.

### Q29. How do you audit OIDC token usage?
CloudTrail for AWS STS AssumeRoleWithWebIdentity events, GCP audit logs for STS token exchanges, correlate on `sub` claim back to namespace/SA. Forward to SIEM.

### Q30. How do you prevent token replay across regions or environments?
Audience claim per environment, short TTL, IP condition where possible, distinct OIDC issuer per cluster, IRSA roles per env with naming convention.

## Secret rotation at scale

### Q31. What is the right secret store for K8s at scale?
External Secrets Operator + Vault or AWS Secrets Manager / GCP Secret Manager / Azure Key Vault. Vault wins for dynamic secrets (DB credentials), cloud-native wins for managed simplicity.

### Q32. How do you rotate a database password without downtime?
Two-credential rotation: app uses cred A, rotate to B in store, ESO refreshes secret in K8s, app reloads (sidecar reloader or SIGHUP), invalidate A. Or use Vault dynamic DB secrets with short TTL and lease renewal.

### Q33. How do you rotate TLS certs at scale?
cert-manager with ACME or internal CA, short-lived certs (24h to 90d), reloader watching Secret to roll Deployments, mesh handles workload certs automatically (Istio rotates SVID hourly).

### Q34. What is the strategy for static secrets that must rotate?
Tag with TTL annotation, scheduled job to rotate via API to source store, ESO syncs, application reads via volume mount with subPath, app code retries on auth failure.

### Q35. How do you prove rotation happened?
Audit log on store side, K8s event on Secret update, metric `secret_age_seconds` exposed by an exporter scraping Secret annotations, alert when `> SLA`.

### Q36. What about sealed-secrets — when is it appropriate?
Small clusters, GitOps-only, no central store. Caveats: rotation requires re-sealing and committing, the sealing key is a single point of trust. Prefer ESO for anything beyond 10 services.

### Q37. How do you prevent a secret from being logged?
Disable RequestResponse audit on Secrets, redact in app logs, lint pipelines for `kubectl get secret -o yaml` in scripts, use `--token-only` flags, ban env vars for highly sensitive secrets — prefer projected volumes.

### Q38. How do you handle secret access during a Vault outage?
Cache last-known value in K8s Secret with ESO, set high refresh interval for non-critical, use Vault Performance Standby, consider regional Vault clusters with replication, fallback to read-only mode in app.

### Q39. How do you grant least privilege on the secret store?
One Vault role per app per env, policies on path `secret/data/env/app/*`, K8s auth method binding SA to role, audit device on Vault streaming to SIEM, deny `*` policies.

### Q40. How do you onboard a new app to External Secrets?
Template: Helm chart includes `ExternalSecret` and `SecretStore` ref, Vault path computed from `{env}/{namespace}/{app}`, SA bound to Vault role via Kubernetes auth, CI bootstraps the Vault role via Terraform on first deploy.

## Runtime detection at scale (Falco / Tetragon)

### Q41. Falco vs Tetragon — which to pick?
Falco: rule-based, mature, kernel module or eBPF, alerts to falcosidekick. Tetragon: eBPF-native, in-kernel filtering and enforcement, lower overhead at high event volume. Use Tetragon for fleets > 500 nodes or where you need policy enforcement, Falco for mature alerting and community rules.

### Q42. What rules do you start with?
Falco default rules + k8s_audit. Highest value: shell in container, write to /etc, mount of sensitive paths, outbound to non-allowlist destination, exec into kube-system, change to RBAC.

### Q43. How do you tune false positives?
Macro overrides in falco_rules.local.yaml, exception lists per workload label, suppression at falcosidekick before SIEM, weekly review of fired rules with action: tune, delete, escalate.

### Q44. How do you ship events at scale?
Falcosidekick to Kafka, downstream consumers: SIEM (Splunk/Elastic), enrichment service adding pod metadata, deduplication, alert manager. Avoid direct SIEM push from each node.

### Q45. What is the cardinality risk?
Per-event labels (pod, image, command) explode metric cardinality. Use logs not metrics for events, keep metrics aggregated by rule + namespace.

### Q46. How do you enforce with Tetragon?
TracingPolicy with `enforcer` action — kill, override return value, signal. Example: kill any process opening `/etc/shadow` outside allowlist. Roll out per-namespace.

### Q47. Detection coverage map?
Map rules to MITRE ATT&CK for Containers. Track coverage per tactic. Aim for detection in: Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Exfiltration.

### Q48. How do you handle a runtime alert at 3am?
Runbook: confirm not noise, isolate pod (NetworkPolicy deny + cordon node if needed), capture forensics (process tree, fd list, /proc/PID/maps), preserve container fs, page IR lead if confirmed, postmortem within 5 days.

## Zero-trust mesh adoption

### Q49. What is zero-trust in K8s terms?
Every connection authenticated and authorized regardless of network position. Identity is workload-bound (SPIFFE), not IP-bound. Default-deny everywhere.

### Q50. Istio vs Linkerd vs Cilium for mTLS?
Linkerd: simplest, lowest overhead, ambient not yet GA. Istio: most features, ambient mode reduces sidecar cost. Cilium: eBPF mTLS without sidecars, integrates with NetworkPolicy. Pick by org maturity and feature need.

### Q51. What is the rollout plan?
Phase 1: install mesh, enable PERMISSIVE mTLS, observe. Phase 2: enable STRICT per-namespace, fix exceptions. Phase 3: AuthorizationPolicy default-deny per namespace, allowlist intentional traffic. Phase 4: extend to ingress and egress.

### Q52. What about non-mesh workloads?
Mesh egress gateway, sidecar injection by namespace label, accept-no-mesh annotation for legacy with explicit risk acceptance, plan migration with deadline.

### Q53. How does SPIFFE fit?
SPIFFE provides workload identity (SVID) — X.509 or JWT — issued by SPIRE. Mesh uses SVIDs for mTLS. Workloads outside mesh use SPIRE agent to fetch SVID for cross-system auth (e.g. Vault, DB).

### Q54. How do you authorize at L7?
AuthorizationPolicy with method, path, JWT claims. Validate JWT at sidecar via RequestAuthentication. Pass principal to app for fine-grained checks.

### Q55. What breaks when you turn on STRICT mTLS?
Probes from kubelet (allow with PERMISSIVE on probe port or use exec probes), prometheus scraping (use mesh-aware Prom or scrape through sidecar), legacy clients without mTLS, headless services (work but require attention).

### Q56. How do you observe mesh traffic?
Mesh exposes metrics (request rate, error rate, p99) and traces (Jaeger/Tempo). Build SLOs from these. Kiali for topology. Hubble for Cilium.

## Compliance program design (PCI / HIPAA / SOC 2)

### Q57. What is the first step of a compliance program?
Scope. Define cardholder data environment (PCI), ePHI systems (HIPAA), or in-scope services (SOC 2). Network segmentation reduces scope dramatically.

### Q58. How do you implement PCI segmentation in K8s?
Dedicated cluster or dedicated namespace + node pool with taints, network policies block all ingress except payment service entry, egress only to PCI-approved endpoints, all logs to a separate SIEM index, all admin via bastion with MFA.

### Q59. How do you handle HIPAA encryption?
At rest: KMS-encrypted etcd, KMS-encrypted PVs, KMS-encrypted object storage. In transit: TLS 1.2+ everywhere, mTLS via mesh, no plaintext intra-cluster.

### Q60. SOC 2 logging requirements?
CC7.2 — monitor system components. Centralized logs with integrity (signed or WORM), retention 1 year, access reviewed quarterly, alerts on detection of unauthorized changes, evidence for auditor.

### Q61. How do you produce evidence at audit time?
Continuous evidence collection: Drata/Vanta/Secureframe pulling from K8s, cloud, IdP, vuln scanner, SIEM. Store as immutable evidence artifacts with timestamps. Auditor gets read-only access.

### Q62. How do you handle change management for SOC 2?
All changes via PR with approval (CC8.1). GitOps enforces this — direct cluster changes denied via RBAC. Emergency change process documented and audited.

### Q63. What about access reviews?
Quarterly: export RBAC bindings, IAM roles, IdP group memberships. Manager attests per direct report. Revoke on no-attestation. Tool: Sailpoint, custom script, or IdP-native review.

### Q64. How do you prove vulnerability management?
Trivy/Snyk in CI, Grype/Trivy continuously against running images, SLA: critical < 7d, high < 30d. Dashboard with MTTR per severity. Auditor sees SLA hit rate.

## Incident response playbooks

### Q65. What are the IR phases?
Prepare, Detect, Analyze, Contain, Eradicate, Recover, Lessons Learned. NIST SP 800-61.

### Q66. What does prepare look like for K8s?
Runbooks per scenario, IR team on-call rotation, tabletop exercises quarterly, forensic tooling pre-installed (sysdig capture, kubectl debug, kube-forensics), evidence pipeline tested, legal/PR contacts known.

### Q67. Compromised pod — playbook?
1) Confirm via Falco/Tetragon evidence. 2) Cordon node. 3) Apply NetworkPolicy deny on pod label. 4) `kubectl debug` to capture process list, network conns, env. 5) Snapshot container fs. 6) Delete pod, evict node, rotate any creds it held. 7) Hunt for lateral movement via audit log.

### Q68. Stolen kubeconfig — playbook?
1) Revoke client cert via CSR deletion or rotate cluster CA (worst case). 2) Disable IdP user. 3) Audit log search for user actions. 4) Inventory created/modified resources, treat as compromised. 5) Rotate any secrets accessed. 6) Postmortem on how it leaked.

### Q69. Cryptojacking detected — playbook?
1) Kill pod, isolate node. 2) Trace image to source — was it pulled from public registry without verification? 3) Block image digest at admission. 4) Check for persistence (DaemonSets, CronJobs, mutating webhooks). 5) Audit all images deployed since the bad pull.

### Q70. Ransomware on PV — playbook?
1) Snapshot PV before any action. 2) Identify infection vector (vuln, creds, supply chain). 3) Restore from clean backup to new namespace. 4) Validate backup integrity before cutover. 5) Rotate all creds in scope. 6) Notify per legal/regulatory requirements (HIPAA 60d, GDPR 72h).

### Q71. Public exposure of S3-equivalent / etcd snapshot — playbook?
1) Lock down ACL immediately. 2) Determine what data was exposed and for how long via access logs. 3) Notify legal. 4) Rotate any credentials/PII keys in the exposed data. 5) Postmortem on bucket policy gap, IaC guardrail to prevent recurrence.

### Q72. How do you measure IR maturity?
MTTD (mean time to detect), MTTR (respond), MTTC (contain), tabletop frequency, runbook coverage of scenarios, % of detections with auto-containment, postmortem completion rate.

## Closing principles

- Default-deny everything: network, RBAC, admission, egress.
- Identity is the new perimeter: SPIFFE for workloads, OIDC for humans.
- Sign and verify everything: image, attestation, config bundle.
- Detect at runtime — preventive controls fail.
- Practice IR before you need it.
- Evidence is continuous, not annual.
