    Visual Flows — 8 Mermaid Diagrams of Strategies in Motion¶

    Each diagram shows a strategy at a specific moment of the rollout: pods being replaced, services flipping, traffic shifting. Read top to bottom — each diagram is a "snapshot" of one phase.

    Flow 1 — Rolling Update: pod-by-pod replacement¶

    A 4-pod Deployment swapping v1 to v2 with maxSurge 1, maxUnavailable 0.

    Mermaid source 
    flowchart LR
  Start[Start: 4x v1] --> S1["Add 1x v2
    now 5 pods"]
  S1 --> S2["Kill 1x v1
    now 4 pods"]
  S2 --> S3["Add 1x v2
    now 5 pods"]
  S3 --> S4["Kill 1x v1
    continue"]
  S4 --> Done[End: 4x v2]

    What is moving: ReplicaSet count. Old RS scales down, new RS scales up, in lockstep, controlled by surge / unavailable settings.

    Flow 2 — Blue/Green: Service selector flip¶

    Two ReplicaSets exist simultaneously. The Service points to one at a time.

    Mermaid source 
    flowchart LR
  U[Users] --> Svc["Service
    selector: blue"]
  Svc --> B["Blue RS v1
    4 pods"]
  G["Green RS v2
    4 pods"] -.idle.-> Wait[Pre-warm]
  Wait --> Flip[Patch selector to green]
  Flip --> Done[Service now routes to Green]

    What is moving: A label-selector edit on the Service. Pod count stays constant; only the routing flips. Rollback = flip the label back.

    Flow 3 — Canary: progressive traffic shift¶

    Argo Rollouts moving traffic 0 -> 10 -> 50 -> 100.

    Mermaid source 
    flowchart LR
  Start["100 percent stable
    0 percent canary"] --> Step1[90 / 10]
  Step1 --> Analyse1["AnalysisRun
    checks SLIs"]
  Analyse1 --> Step2[50 / 50]
  Step2 --> Analyse2["AnalysisRun
    checks SLIs"]
  Analyse2 --> Done[0 / 100]

    What is moving: Weights in the TrafficRouting resource (Istio VirtualService, SMI TrafficSplit, or NGINX canary annotation). Pods stay running on both sides until promotion completes.

    Flow 4 — Shadow / Mirror: traffic copied, responses discarded¶

    Real users hit stable. A copy of each request goes to shadow.

    Mermaid source 
    flowchart LR
  U[User Request] --> Mesh[Sidecar Proxy]
  Mesh --> Stable["Stable v1
    responds to user"]
  Mesh -.mirror copy.-> Shadow["Shadow v2
    processes silently"]
  Shadow --> Drop[Response dropped]
  Stable --> User2[User receives]

    What is moving: A mirror directive in the VirtualService. The proxy duplicates the request; only the original path returns to the user.

    Flow 5 — A/B Testing: header-based routing¶

    Routes are decided per-request based on a header value.

    Mermaid source 
    flowchart LR
  U[Request] --> GW[Gateway]
  GW --> Match{Header
    x-experiment?}
  Match -->|group-a| A[Variant A]
  Match -->|group-b| B[Variant B]
  Match -->|none| Default[Default Stable]

    What is moving: Nothing on the cluster after setup. The router evaluates each request and picks a destination subset based on rules. Experiments are observed via downstream analytics.

    Flow 6 — Multi-cluster Blue/Green: global LB flip¶

    Two full clusters. A global load balancer steers traffic.

    Mermaid source 
    flowchart LR
  Users[Global Users] --> GLB[Global Load Balancer]
  GLB -->|100 percent| C1["Cluster Blue
    region us-east"]
  GLB -.0 percent.-> C2["Cluster Green
    region us-west"]
  Flip[Update GLB weights] --> GLB
  C2 --> Ready[Pre-validated via synthetics]

    What is moving: GLB backend weights (or weighted DNS records). A single config change at the edge swings all global traffic between clusters.

    Flow 7 — Canary with SLO gate (auto-abort path)¶

    Argo Rollouts AnalysisRun fails — rollout reverses.

    Mermaid source 
    flowchart LR
  Step[Step 3: 50 percent] --> Analyse["AnalysisRun
    queries Prometheus"]
  Analyse --> Decision{p99 latency OK?
    error rate OK?}
  Decision -->|Pass| Promote[Promote to 100 percent]
  Decision -->|Fail| Abort[Abort: shift back to stable]
  Abort --> Stable[100 percent stable v1]

    What is moving: The AnalysisRun executes metric queries. On failure, Argo flips traffic back to stable and scales the canary RS down. On success, it advances to the next step in the strategy spec.

    Flow 8 — Rolling Update with PDB and HPA interactions¶

    Real-world rolling: probes, PDB, and HPA all engage simultaneously.

    Mermaid source 
    flowchart TB
  Trigger[kubectl set image] --> RS[New ReplicaSet created]
  RS --> Surge[maxSurge pod started]
  Surge --> Probe[readinessProbe wait]
  Probe --> PDB{PDB allows
    termination?}
  PDB -->|Yes| Kill[Old pod terminated]
  PDB -->|No| Wait[Block until safe]

    What is moving: ReplicaSet controller, kubelet probes, PDB controller, and optionally HPA all coordinate. The PDB acts as a brake — if too few pods would remain ready, the rollout pauses until availability returns.

    Bonus: lifecycle of a single pod during rolling update¶

    Mermaid source 
    flowchart LR
  Pending[Pending] --> Init[Init containers]
  Init --> Start[Container start]
  Start --> Startup[startupProbe]
  Startup --> Ready["readinessProbe
    passes"]
  Ready --> Serve[Receives traffic]

    What is moving: Pod phase transitions. A new pod is "Ready" only after all probes pass; only then does the Service endpoint controller add it to the active pool. Old pods enter Terminating phase, drained via preStop hook + terminationGracePeriodSeconds.

    Flow comparison: traffic shape over time¶

    Mermaid source 
    flowchart LR
  R["Rolling: gradual
    pod swap"] --> O1["Mixed v1 plus v2
    during window"]
  B["Blue Green: instant
    flip"] --> O2["100 percent v1 then
    100 percent v2"]
  C["Canary: stepped
    weights"] --> O3["1 then 10 then 50
    then 100 percent v2"]

    Reading the diagrams¶

    • Solid arrow = active traffic or state transition.
    • Dotted arrow = mirror, idle, or alternate path.
    • Diamond = decision gate (probe, analysis, PDB).
    • Rectangle = pod, RS, Service, or controller action.

    How to extend these for your team¶

    1. Replace generic labels with your service names.
    2. Add observability hooks (Prometheus targets, Datadog tags).
    3. Annotate each transition with the kubectl / argo command that triggers it.
    4. Render in Backstage or your wiki for onboarding.

    Flow 9 — Argo Rollouts BlueGreen with preview Service¶

    A second Service (the preview Service) lets you test green before flipping the active Service.

    Mermaid source 
    flowchart LR
  Active[Active Service] --> Blue[Blue v1 Pods]
  Preview[Preview Service] --> Green[Green v2 Pods]
  Tester[QA + synthetics] --> Preview
  Promote[Promote command] --> Flip[Active points to Green]

    What is moving: Two Services with different selectors. The Rollout controller swaps both selectors when promoted. The preview Service is the secret weapon — full smoke testing on green before any user is touched.

    Flow 10 — Flagger canary with automatic rollback¶

    Flagger watches metrics each interval and auto-aborts on breach.

    Mermaid source 
    flowchart LR
  Start[Canary deployed] --> Step[Increase 10 percent]
  Step --> Metric[Query Prometheus]
  Metric --> Gate{Threshold OK?}
  Gate -->|Yes| Next[Next step]
  Gate -->|No| Rollback[Auto rollback to primary]

    Flow 11 — Database-backward-compat dance¶

    The danger zone — schema must serve both versions during the rollout.

    Mermaid source 
    flowchart LR
  V1[App v1 reads col_a] --> DB["Database
    col_a + col_b"]
  V2[App v2 reads col_b] --> DB
  DB --> Both[Both versions happy]
  Cleanup[Drop col_a after v1 gone] --> DB

    What is moving: Two-phase migration. Add new column, deploy code that writes both, deploy code that reads new, then drop old. Never combine schema change with code change in one rollout.

    Flow 12 — Argo Rollouts experiment (sidecar canary for analysis)¶

    An Experiment runs a temporary canary purely for measurement, separate from the user-facing rollout.

    Mermaid source 
    flowchart LR
  Stable[Stable RS] --> Users[Users]
  Exp[Experiment RS] --> Synth[Synthetic load]
  Synth --> Metric[Compare metrics]
  Metric --> Verdict{Pass?}
  Verdict -->|Yes| Promote[Allow real rollout]

    Reading-the-code map¶

    When you open a Rollout manifest, here is which YAML field maps to which visual element above:

    YAML field Visual element
    strategy.canary.steps Flow 3 traffic shift
    strategy.canary.analysis Flow 7 SLO gate
    strategy.blueGreen.activeService Flow 2 active arrow
    strategy.blueGreen.previewService Flow 9 preview arrow
    trafficRouting.istio.virtualService Flow 4 mirror, Flow 5 header match

    End of visual flows.
